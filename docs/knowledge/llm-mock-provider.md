# 知识点：用 Mock LLM 做离线开发与测试

这一类知识点解决**如何在不花真钱、不依赖外网的情况下，把 Agent 流程开发和测试推进下去**。

## 1. Mock 的本质：让"模型"成为可注入的确定性依赖

**知识点**：真实 LLM 是"慢、贵、不稳定、有配额"的外部依赖。测试和本地开发应该把"模型调用"替换成**确定性、即时、免费**的假实现，让流程只测编排逻辑，不测模型能力。

**为什么**：如果测试依赖真实模型，会慢、会花钱、会因网络/配额随机失败，CI 无法稳定。

**可复用规则**：任何外部/昂贵/易变依赖，都要留一个可注入的 mock 位（本项目通过配置开关 `LLM_PROVIDER=mock` 或测试里 patch 实现）。

## 2. 识别"这次在调哪个角色"：用内容识别，别用调用顺序

**知识点**：模型调用是无状态的，mock 无法靠"第几次调用"判断该返回 Planner 还是 Reviewer 的输出。**可靠的做法是识别传入的 system prompt 关键词**，据此返回对应角色的输出。

**为什么**：调用顺序是多变的（循环、重试、分支），会随流程演进失效；而角色的 system prompt 是稳定契约。

**可复用规则**：mock 的真实性来自"它读到了什么"，而不是"它被第几次调用"。让 mock 依据输入内容（system prompt / user 文本）决定响应。

## 3. 用"可观测标记"打造确定性状态机

**知识点**：要测重写循环这类多轮逻辑，mock 得能**确定性**地表达"这次不通过、重写后通过"。做法是：让参与方在返回内容里埋标记，下一轮 mock 读到标记就切换行为。

**为什么要确定性**：如果 mock 每次随机说 pass/revision，测试结果不可复现，就无法验证循环逻辑。

**可复用规则**：mock 不是"随机回答"，而是**根据输入里是否出现某个标记，返回预先设计好的序列**——这是把"模型行为"变成"可断言的测试夹具"的关键。

## 4. 测试里 patch 的位置：patch 引用点，不是定义点

**知识点**：mock 要在"依赖被使用的地方"接管，而不是在"依赖被定义的地方"。

**为什么**：如果 patch 的是定义处，而调用方 import 的是另一个名字，patch 不会生效，测试悄悄跑的是真实实现。

**可复用规则**：用 `patch("模块A.模块B.func")` 时，路径要写**调用方所在模块**里的引用名，而不是原始定义模块。这也是"面向接口"之外，另一条保证可测性的纪律。

## 5. Mock 的三条纪律

1. **只覆盖流程，不冒充模型质量**：mock 的 JSON 永远合法、难度固定，不能用来评估真实模型质量。
2. **范围从成功路径开始**：先让 happy path 稳定，再按需扩展模拟错误（超时、非法 JSON），别一上来堆太多分支。
3. **保持与真实契约一致**：mock 返回的结构（字段名、类型）必须和真实模型一致，否则测试通过但上线就崩。

## 6. 一句话总结

Mock LLM 的正确姿势是：**作为可注入的确定性依赖 + 依内容识别角色 + 用标记构造可断言的状态机 + patch 引用点 + 只测流程不冒充质量**。
