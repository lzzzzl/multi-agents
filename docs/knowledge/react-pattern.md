# 知识点：ReAct —— 让 Agent 边想边做的循环范式

这一类知识点解决**如何让 Agent 在推理与行动之间交替推进，用外部世界的反馈修正推理，而不是一次性拍脑袋给答案**。

## 1. ReAct 是什么

**知识点**：ReAct 是 **Reasoning + Acting**（推理 + 行动）的缩写，最早由 Yao et al. 在 2022 年的论文《ReAct: Synergizing Reasoning and Acting in Language Models》提出。它定义了一种让 LLM 在解决复杂任务时，把“想”和“做”交替进行的工作方式。

**为什么**：传统上有两种用法，各有明显短板：

- **只推理（Reasoning-only）**：例如 Chain-of-Thought，让模型把思考过程一步步写出来再作答。问题是模型在“脑内空想”，没有外部信息，容易幻觉、知识过时。
- **只行动（Acting-only）**：模型直接调用工具，但不做显式思考。问题是缺乏规划，容易做出一连串盲目操作。

ReAct 的洞见是：**把推理和行动交错融合**，让模型在一个循环里反复执行“思考 → 行动 → 观察”，从而既能靠推理制定计划，又能靠行动获取真实信息并修正判断。

## 2. 一个循环：Thought → Action → Observation

**知识点**：ReAct 循环由几个交替出现的要素组成：

- **Thought（思考）**：模型用文字写出当前分析和下一步计划。
- **Action（行动）**：执行一个具体的外部操作（搜索、计算器、查询数据库、调用 API）。
- **Observation（观察）**：外部环境返回结果，作为新信息输入模型。
- 最终 **Answer / Finish**：当信息足够时输出最终答案并结束。

**为什么**：每一步行动都由前面的推理决定，每一步观察又反过来修正后续推理。这就是“推理指导行动，行动反馈推理”的协同。

一个经典示例（“蒂芙尼的爸爸有多少个孩子？”）：

```text
Thought 1：我需要先找到“蒂芙尼”是谁。
Action 1：Search["蒂芙尼 爸爸"]
Observation 1：... 返回结果：蒂芙尼的父亲是某某某 ...

Thought 2：我还需要知道蒂芙尼的兄弟姐妹情况。
Action 2：Search["某某某 有几个孩子"]
Observation 2：... 返回结果：他有 5 个孩子 ...

Thought 3：已经找到答案，可以作答。
Answer：蒂芙尼的爸爸有 5 个孩子。
```

用伪代码表达这个循环：

```text
context = 初始问题
while not finish(context):
    thought, action = llm.reason(context)   # 模型决定下一步怎么想、做什么
    if action is None:
        return llm.answer(context)          # 信息够了，给出最终答案
    observation = execute(action)           # 真正执行工具，拿到外部结果
    context.append(thought, action, observation)
```



## 3. 为什么 ReAct 有效

**知识点**：ReAct 的价值来自几个方面：

- **减少幻觉**：模型不再凭空编造，而是通过工具获取可验证的事实。
- **处理长程任务**：复杂问题往往需要多步，循环结构天然支持逐步推进。
- **可解释、可调试**：Thought 以自然语言呈现，能直接看到模型的“内心活动”。
- **动态纠错**：一次行动结果不对时，可以根据观察调整策略，而不是一次性输出。
- **接入外部世界**：把 LLM 从“静态生成器”变成能感知环境、采取行动、再感知反馈的智能体。



## 4. 与其他范式的对比


| 方法                    | 特点           | 局限                      |
| --------------------- | ------------ | ----------------------- |
| Chain-of-Thought（CoT） | 只推理，写出完整思考链  | 无外部信息，易过时 / 幻觉          |
| Act-only              | 只调用工具，不做显式思考 | 缺乏规划，易盲目行动              |
| ReAct                 | 推理与行动交替进行    | 更复杂，token 消耗更多，需要定义动作空间 |


论文中的实验表明：在需要外部知识、事实性要求高的任务上（问答、事实核查等），ReAct 比单纯 CoT 或单纯行动更可靠；而在纯推理任务上 CoT 仍有优势。二者其实互补，现代实践常常结合使用。

## 5. 落地到本项目：当前形态与差距

**知识点**：本项目的 Agent 目前是“一个 Agent 声明一次工具调用”的简化形态，可以看作 ReAct 的**单轮动作特例**，还不是完整的多轮循环。

**为什么**：

- `BaseAgent.run`（`backend/app/agents/base.py`）只构造一次 prompt、调用一次 LLM、解析一次结构化输出，没有“行动后再观察再思考”的循环。
- `ResearcherAgent`（`backend/app/agents/researcher.py`）只声明一个 `tool_use`，由 workflow 交给 `ToolRunner` 执行，之后不再把结果喂回模型做下一轮推理。
- 工作流是顺序编排的（Planner → Researcher → Writer → Reviewer），多轮工具循环的能力还未引入。

**可复用规则**：若要演进成真正的 ReAct 循环，需要在现有基础上补上这几块：

1. 把 `Observation`（工具结果）作为下一条消息注入回 LLM 上下文。
2. 定义**停止条件**（模型输出“已完成”或无工具调用时退出）。
3. 设置**最大迭代次数**，避免死循环。
4. 每一轮都通过 `ToolRunner` 执行并记录 `ToolCall` + 事件，沿用现有的审批与审计能力。



## 6. 实现 ReAct 循环的可复用 checklist

新增一个“多轮工具循环 Agent”时，按这套顺序走：

1. 定义**动作空间**（可用工具清单 + 参数 schema，复用 `tools/registry`）。
2. 在 system prompt 中明确 **Thought / Action / Observation / Finish** 的输出格式。
3. 定义**停止条件**与**最大迭代轮数**。
4. 把每次工具结果**结构化地追加**到后续 prompt 的 Observation 里。
5. 对 Action 输出做**容错解析**（剥代码块、截 JSON、缺字段兜底），参考 `agent-architecture.md`。
6. 每次工具调用走 `ToolRunner`，高风险工具保留**人工审批**。
7. 记录每轮 `ToolCall`、事件与耗时，方便审计和重放。
8. 加**循环上限**与失败回退的单元测试。



## 7. 常见坑

- **死循环**：模型反复调用同一个无效工具，必须设最大轮数并检测重复 Action。
- **token 膨胀**：把完整思考轨迹全塞进上下文会让成本快速上升，可考虑压缩历史或只保留关键 Observation。
- **动作空间过大**：工具太多会让模型选错，按任务裁剪工具集。
- **幻觉参数**：模型可能编造不存在的工具名或参数，解析层要校验并明确报错。
- **过早结束**：模型还没拿到关键信息就输出 Finish，可在 prompt 里加“必须基于 Observation 回答”的约束。



## 8. 一句话总结

ReAct 让 Agent 通过“**思考 → 行动 → 观察**”的循环，把内在推理和外部信息交互结合起来，从而更可靠地解决复杂、多步、需要外部知识的任务；本项目的 Agent 是它的“单轮动作”雏形，演进方向就是补上“把观察喂回模型 + 停止条件 + 迭代上限”这三块。
